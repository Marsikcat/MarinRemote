# Протокол MarinRemote, версия 1

Одно QUIC-соединение (iroh) на сеанс, ALPN `marinremote/1`. Зритель набирает хост по
публичному ключу Ed25519. TLS-рукопожатие QUIC доказывает обеим сторонам ключ собеседника,
поэтому отдельной проверки личности поверх нет.

## Код подключения

```
mr-<base58( [версия 1][ключ: 32][длина метки][метка ретранслятора][sha256(...)[:2]] )>
```

Ретрансляторы n0 сокращаются до короткого имени (`euw1-1`), другие хранятся целиком.
IP-адресов в коде нет: iroh узнаёт их сам. Вместо кода можно вставить ключ целиком (64 hex).
Отпечаток для сверки на глаз — 8 символов base32 (Crockford) от sha256 ключа: `7K3M-Q9XA`.

**Ссылка** — тот же код со схемой: `marinremote://mr-…`. Принимаются и варианты, которые
делают из неё браузеры: `/` в конце, `?…`/`#…`, %-экранирование, `marinremote:mr-…`.
Обработчик схемы — `HKCU\Software\Classes\marinremote\shell\open\command` =
`"…\MarinRemote.exe" --connect "%1"`. Второй запуск передаёт ссылку уже запущенной копии
через локальный сокет (`connect <ссылка>`); подключение начинается только после «Да» в окне
«Подключиться к …?».

## Поиск в локальной сети

UDP-широковещание на порт 8894 раз в 2 с, только если на хосте включено «Виден в локальной сети»:

```json
{"app": "MarinRemote", "proto": 1, "id": "<ключ hex>", "port": 8895, "name": "DESKTOP-…"}
```

## Управляющий стрим (двунаправленный, JSON-строки, до 1 МБ, приоритет 3)

Его открывает зритель. Первое сообщение — `hello`. До ответа `auth ok` хост:

- не обрабатывает других строк (игнор + `pre_auth` в журнал);
- не принимает датаграммы: в каждой должна быть метка сеанса, которой до входа не знает никто;
- не принимает uni-стримы: в заголовке каждого должен быть `sid` из `auth ok`.

`hello` не пришёл за 10 с — соединение закрывается.

```
→ {"t":"hello","app":"MarinRemote","proto":1,"ver":"0.1.0","name":"Ноутбук",
   "want":["view","control","files","clipboard"],
   "password":"…"?,        только для входа по паролю
   "resume":"…"?,          токен повторного входа
   "remember":true?,       просьба запомнить устройство (лишь подсказка в окне запроса)
   "pair":{…}?}            просьба связать ПК — см. «Связывание»
← {"t":"auth.wait","timeout":30}
← {"t":"auth","ok":true,"sid":"<16 hex>","rights":["view","control"],"resume":"<токен>",
   "remembered":"contact"|"password"|"ask"|null,
   "host":{"name":"…","ver":"…","relay":"…","addrs":[…]}}
← {"t":"auth","ok":false,"reason":"denied|timeout|bad_password|locked|cooldown|blocked|off|busy|version|protocol",
   "retry_after":12?}
```

После входа обе стороны раз в 5 с шлют `{"t":"ping"}`, если больше нечего. Если 20 с ничего
не приходит, соединение считается потерянным.

| Сообщение (зритель → хост) | Нужное право |
|---|---|
| `ping`, `bye` | — |
| `monitor`, `video.key`, `video.quality`, `video.pause`, `clock` | view |
| `clip` | clipboard |
| `fs.roots`, `fs.list`, `fs.mkdir`, `fs.rename`, `fs.delete`, `get`, `put`, `put.end`, `xfer.cancel` | files |
| `power` | control |

Сообщение без нужного права игнорируется. Первый случай каждого вида пишется в журнал
(`violation`), счётчик — при конце сеанса. Неизвестные типы игнорируются молча: это
задел на совместимость с более новыми версиями.

Хост → зритель: `{"t":"rights","rights":[…]}` — права изменились посреди сеанса (см. «Права»),
остальное — ниже.

**Питание** (право `control`):

```
→ {"t":"power","action":"lock|restart|shutdown|cancel"}
← {"t":"power.ok","action":"lock","delay":0}
← {"t":"power.ok","action":"restart|shutdown","delay":30}     shutdown.exe /r|/s /t 30 /c "MarinRemote: <имя зрителя>"
← {"t":"power.error","action":"…","msg":"…"}                 уже назначено / Windows отказала
← {"t":"power.cancelled","action":"restart|shutdown","by":"viewer|host"}   всем сеансам с управлением
```

`lock` — `LockWorkStation`. Перезагрузку или выключение отменяют `cancel` от зрителя или кнопка
«Отменить» в окне на хосте (`shutdown /a`). Одновременно назначено не больше одного. Каждая
команда пишется в журнал (`power`).

## Видео

```
← {"t":"monitors","current":0,"list":[{"id":0,"name":"Экран 1 (основной)","x":0,"y":0,"w":1920,"h":1080,"primary":true}]}
→ {"t":"monitor","id":1}                         показывать другой экран
→ {"t":"video.quality","preset":"auto|smooth|sharp|low"}
→ {"t":"video.key"}                              картинка сломалась — нужен ключевой кадр
→ {"t":"video.pause","on":true}                  окно свёрнуто — кадры не нужны
← {"t":"video.state","state":"starting"|"ok"|"unavailable","mon":0,"w":1920,"h":1080,"fps":60,
   "kbps":20000,"encoder":"NVENC","capture":"ddagrab","quality":"auto","step":0,
   "reason":"secure_desktop|error|no_monitor"?}
← {"t":"cursor","id":"<12 hex>","w":32,"h":32,"hx":1,"hy":1,"bgra":"<base64(zlib(premultiplied BGRA))>"}
← {"t":"cursor","id":"<12 hex>"}                 форма, которая у зрителя уже есть
→ {"t":"clock","v":<мкс зрителя>}   ← {"t":"clock","v":…,"h":<мкс хоста>}   смещение часов для замера задержки
```

**Кодирование.** Отдельный процесс (`app.py --encoder`):
- ddagrab отдаёт D3D11-кадры прямо в NVENC; x264, масштаб и мониторы чужого видеоадаптера идут
  через gdigrab в системной памяти.
- Настройки: без B-кадров, `tune ull` / `zerolatency`, без lookahead, VBV ≈ 100 мс.
- Ключевой кадр — по запросу (`forced-idr`), страховочный раз в 10 с; SPS/PPS перед каждым.
- Rate control — VBR с потолком (`maxrate` = цель). CBR у NVENC добивает каждый кадр
  заполнителем до полной скорости: 20 Мбит/с даже на неподвижном рабочем столе. VBR с тем же
  потолком и тем же буфером даёт ту же границу задержки, а неподвижный экран почти ничего
  не стоит.
- Курсор в кадр не рисуется.

| Пресет | Разрешение | к/с | потолок, Мбит/с |
|---|---|---|---|
| `auto` | исходное; через ретранслятор до 1080p | 60 / 30 | 20 / 6, при отставании ступенями до 720p · 3 |
| `smooth` | исходное | 60 | 20 |
| `sharp` | исходное | 30 | 15 |
| `low` | 720p | 30 | 4 |

**Сегменты и отставание.** Кадры идут uni-стримами, сегмент = стрим, начинается с ключевого
кадра. Зритель ~20 раз в секунду подтверждает датаграммой 3, сколько кадров сегмента получил.

Хост сбрасывает сегмент (`RESET_STREAM`), если:
- кадр висит без подтверждения дольше max(150 мс, 2·RTT + 50 мс) — для ключевого вчетверо дольше;
- QUIC не забирает кадры дольше ~100 мс.

После сброса QUIC выбрасывает всё, что ещё лежало в его буфере. Хост просит у кодировщика
ключевой кадр, и следующий сегмент начинается с него. Выбрасываются только целые кадры.

**Режим `auto`:**
- **вниз:** три сброса за 15 с опускают качество на ступень;
- **вверх:** после 20 с без сбросов качество поднимается на ступень, до потолка своего пути
  (напрямую — ступень 0, через ретранслятор — ступень 2). Поэтому качество растёт само, когда
  iroh переводит соединение с ретранслятора на прямой путь;
- **без качелей:** если подъём меньше чем через 30 с кончился откатом, следующая попытка ждёт
  вдвое дольше (до 5 мин). Подъём, который продержался минуту, возвращает ожидание к 20 с.

**Неподвижный экран ничего не стоит.** Чтобы держать частоту, ddagrab отдаёт неизменившуюся
картинку повторно — ссылкой на ту же D3D11-текстуру. Кодировщик такие повторы не кодирует и
не отправляет; зритель просто показывает последний кадр. Исключение — нужен ключевой кадр:
тогда ближайший повтор кодируется как ключевой, ждать изменения экрана не нужно. Курсор
приходит отдельно и в кадры не попадает. В итоге при неподвижном экране нет ни кодирования,
ни трафика картинки, ни декодирования у зрителя.

**Потеря захвата.** ddagrab сам не восстанавливается, когда Windows отзывает дублирование
экрана (`DXGI_ERROR_ACCESS_LOST`): кодировщик выходит с кодом 4, и хост перезапускает его
через 0,2 с. Если потеря повторилась дважды за 10 с — например, монитор подключён к другой
видеокарте, — этот монитор снимается через Windows.Graphics.Capture (`CreateForMonitor`,
кадры остаются на видеокарте, неизменившийся экран тоже не кодируется), а если её нет —
через GDI. Зритель в обоих случаях «недоступно» не видит.

**Кодировщик хоста общий** для всех зрителей одного монитора с одним качеством.

## Файлы

**Пути — только виртуальные:** `<id корня>/<относительный путь>`, разделитель `/` или `\`.
Корни — папки, которые человек у хоста открыл в «Доступе»; по умолчанию папка пользователя.

Хост проверяет путь дважды:
1. **По тексту.** Отказ сразу:
   - `..`, `.`, пустые части, путь с `/` или `\` в начале;
   - буквы дисков и `:` (альтернативные потоки);
   - UNC и `\\?\`;
   - имена устройств (CON, NUL, COM1…);
   - символы `<>"|?*`, точка или пробел в конце имени.
2. **По сути.** Файл или папка открывается, и окончательный путь дескриптора
   (`GetFinalPathNameByHandle`) обязан лежать внутри окончательного пути корня. Так ловятся
   символические ссылки и junction’ы наружу. Читается и пишется ровно тот дескриптор, что
   прошёл проверку, поэтому подменить папку между проверкой и записью не выйдёт.

```
→ {"t":"fs.roots","id":1}                      ← {"t":"r","id":1,"ok":true,"roots":[{"id":"home","label":"Папка пользователя"}]}
→ {"t":"fs.list","id":2,"path":"home/Документы"}
← {"t":"r","id":2,"ok":true,"path":"home/Документы","entries":[{"n":"a.txt","d":false,"s":10,"m":1792740000,"h"?:true,"l"?:true}]}
→ {"t":"fs.mkdir","id":3,"path":"home/Документы/Новая"}
→ {"t":"fs.rename","id":4,"path":"home/a.txt","name":"b.txt"}       только в той же папке
→ {"t":"fs.delete","id":5,"path":"home/b.txt"}                      в корзину, не насовсем
← {"t":"r","id":…,"ok":false,"code":"denied|bad_path|not_found|exists|not_dir|io","msg":"…"}
```

**Передача.** Каждый файл идёт отдельным uni-стримом, сырыми байтами, без ограничения
размера, с приоритетом −1 (ниже видео и ввода).

Скачивание (хост → зритель):

```
→ {"t":"get","x":"<id>","path":"home/a.iso","offset":N,"size":S,"mtime":M}    size/mtime — при докачке
← {"t":"get.ok","x":…,"size":S,"mtime":M}   и стрим {"t":"file","x":…,"offset":N} + байты [N, S)
← {"t":"xfer.done","x":…,"sha256":"<всего файла>"}
← {"t":"xfer.error","x":…,"code":"changed"}   файл изменился с прошлого раза — зритель начинает заново
```

Зритель пишет в `имя.mrpart`, а рядом кладёт `имя.mrpart.json`: какой ПК, какой файл,
размер, время. Докачка идёт с размера части, если описание совпадает.

Загрузка (зритель → хост):

```
→ {"t":"put","x":…,"path":"home/Рабочий стол/b.zip","size":S,"mtime":M,"overwrite":false}
← {"t":"put.ok","x":…,"offset":N}            N — сколько у хоста уже есть от этого файла
   стрим {"t":"file","x":…,"offset":N} + байты [N, S), затем
→ {"t":"put.end","x":…,"sha256":"<всего файла>"}
← {"t":"xfer.done","x":…,"sha256":…,"name":"b (1).zip"}   имя, под которым файл лёг
```

У хоста часть файла хранится скрыто: `.<имя>.<sha256(ключ|имя|размер|время)[:10]>.mrpart`.
Поэтому чужая или другая версия файла её не продолжит. Части, к которым не вернулись за
неделю, удаляются при следующей загрузке в ту же папку.

**Общие правила для обеих сторон:**
- **Проверка.** Получатель переименовывает часть в итоговое имя, только когда SHA-256 всего
  файла совпал с присланным. Не совпал — часть удаляется, передача завершается ошибкой
  `hash`.
- **Отмена.** `xfer.cancel` удаляет часть, а обрыв её сохраняет.
- **Продолжение.** После обрыва сеанс восстанавливается по токену, и незаконченные передачи
  продолжаются сами. Список незаконченных лежит у зрителя в `transfers.json` и переживает
  перезапуск.
- **Журнал хоста.** Каждая передача пишется как `file_get` / `file_put` с итогом: `ok`,
  `interrupted`, `cancelled`, `hash` или код ошибки. Там же размер, SHA-256 и с какого места
  продолжили.

## Буфер обмена

```
↔ {"t":"clip","text":"…"}      текст до 1 000 000 символов, в обе стороны
```

Хост принимает `clip` только при праве `clipboard` и шлёт свой буфер только сеансам с этим
правом. Обе стороны отправляют лишь то, что скопировано во время сеанса. Не отправляются:
- текст, который сами только что получили с другой стороны (так нет эха);
- копии с отметкой «частное»: `ExcludeClipboardContentFromMonitorProcessing`,
  `Clipboard Viewer Ignore`, `CanIncludeInClipboardHistory` = 0,
  `CanUploadToCloudClipboard` = 0.

## Мышь и клавиатура

Координаты — 0..65535 поперёк монитора, который смотрит зритель. Хост переводит их в
пиксели монитора, а затем в единицы `SendInput` (`MOUSEEVENTF_ABSOLUTE | VIRTUALDESK`):
ровно в тот пиксель, включая мониторы левее основного.

- **Движение** — датаграммой 1, не чаще раза в 4 мс. Потерянная или опоздавшая не страшна:
  хост играет только номер новее всех виденных.
- **Кнопки, колесо и клавиши** — по стриму `input`, надёжно и по порядку, с теми же номерами.
  Поэтому опоздавшая датаграмма не утащит курсор назад после клика. Строки стрима:

```
{"m":"down"|"up","b":"left|right|middle|x1|x2","x":…,"y":…,"s":<seq>}
{"m":"wheel","dx":0,"dy":-120,"x":…,"y":…,"s":<seq>}     120 = один щелчок колеса
{"k":<скан-код>,"e":0|1,"d":1|0,"vk":<vk>}             e — extended (E0), vk — подсказка
{"rel":"all"}                                         отпустить всё (окно зрителя потеряло фокус)
```

**Клавиши** — скан-коды, не символы: что они напечатают, решает раскладка хоста.
Pause, Num Lock и Ctrl+Break Windows сообщает со странными скан-кодами — их хост играет
по `vk`.

**Хост помнит**, что держит нажатым каждый сеанс. Всё это отпускается:
- при `rel:all`;
- при конце сеанса и обрыве;
- при потере права управления.

Отпустить можно только то, что этот сеанс нажал сам.

**В окна MarinRemote ввод не попадает.** Клик или колесо над ними, а также клавиша, пока
окно MarinRemote впереди, — отбрасываются. Иначе зритель мог бы сам нажать «Разрешить» или
поменять настройки доступа. Зритель получает `{"t":"warn","code":"self"}`, в журнал пишется
`self_input`.

**Чего ввод не достигнет**, хост проверяет каждые 0,5 с и сообщает при смене:

```
← {"t":"warn","code":"uipi","app":"Taskmgr.exe"}   впереди окно с более высоким уровнем целостности (администратор)
← {"t":"warn","code":"secure","app":""}            защищённый рабочий стол: UAC, Ctrl+Alt+Del, блокировка
← {"t":"warn","code":null,"app":""}                всё снова доступно
```

**Системные клавиши у зрителя.** Пока окно сеанса впереди, хук `WH_KEYBOARD_LL` в отдельном
потоке забирает все клавиши, включая Win, Alt+Tab, Alt+F4, и отправляет их на хост.
Не трогаются:
- чужие инжектированные нажатия (`LLKHF_INJECTED`);
- поддельный Ctrl от AltGr.

Ctrl+Alt+Enter остаётся у зрителя — это полный экран. Ctrl+Alt+Del и Win+L перехватить
нельзя.

## Права

`view` — экран, `control` — мышь и клавиатура, `files` — файлы, `clipboard` — буфер обмена.
Права проверяет хост на каждом сообщении, стриме и датаграмме.

**Права на ходу.** Хост может забрать у сеанса любое из выданных при входе прав и вернуть
его («Забрать управление» / «Вернуть управление»), но не выдать сверх выданного. Зритель
получает `{"t":"rights",…}`. Что он успел отправить с забранным правом, хост отбрасывает
молча, без `violation`; стримы такого права (поток ввода живёт весь сеанс) остаются
открытыми, но ничего не исполняют. Забранное управление отпускает всё нажатое, забранные
файлы останавливают передачи (части для докачки остаются). Токен повторного входа помнит
и текущие права, и выданные: после обрыва зритель возвращается с текущими, а хост по-прежнему
может вернуть остальное. Каждое изменение — запись `rights` в журнале.

## Решение о входе (хост)

1. Ключ в чёрном списке → `blocked`. Подключения выключены → `off`.
2. Есть действующий `resume`-токен этого ключа → вход с теми же правами (∩ `want`).
3. Ключ запомнен и включено «Пускать запомненные без подтверждения»:
   - режим `contact` — сразу, с правами записи ∩ `want`;
   - режим `password` — если задан пароль и он прислан: argon2id-проверка, по одной за раз.
4. Иначе — окно подтверждения на 30 с. Не больше одного окна на ключ и трёх сразу.
   После «Отклонить» ключ 60 с получает `cooldown`.

Неудачные пароли: на ключ 3 попытки без задержки, затем 2, 4, 8 … с, максимум 15 мин.
Больше 20 неудач за 10 мин от кого угодно — пауза 5 мин для всех. Счётчики хранятся
в `auth_state.json` и переживают перезапуск.

**Токен повторного входа.** Одноразовый, привязан к ключу, хранится только его sha256.
Действует, пока жив его сеанс (зритель может вернуться раньше, чем хост заметил обрыв),
и 60 с после обрыва. Аннулируется, если зритель ушёл сам (`bye`), если хост нажал
«Отключить», при блокировке и при аварийном отключении.

## Связывание

Два своих ПК запоминают друг друга. Связывается A (набирает), B отвечает. Пока это не сеанс:
`auth ok` не приходит никогда, соединение заканчивается ответом `pair`.

```
→ hello {…, "want":[все права], "pair":{"commit":sha256(nA) hex,"relay":…,"addrs":[…]}}
← {"t":"pair.nonce","n":nB hex}                 32 случайных байта B
→ {"t":"pair.reveal","n":nA hex}                 должно совпасть с commit, иначе auth protocol
← {"t":"auth.wait","timeout":60}
← {"t":"pair","ok":true,"name":…,"rights":[права A на B],"relay":…,"addrs":[…]}   (закрытие, код 0)
← {"t":"auth","ok":false,"reason":…}            как при обычном входе
```

Код для сверки на обоих экранах — 6 цифр:
`sha256("MarinRemote pair v1" ‖ ключ A ‖ ключ B ‖ nA ‖ nB)[:8] mod 10⁶`, вида `123 456`.
A обязуется своим числом до того, как увидит nB, а B выдаёт nB до того, как увидит nA, —
поэтому тот, кто сидит посередине (например, разослал в сети объявление с чужим именем),
не может подобрать ключи или числа так, чтобы коды на двух экранах совпали: у него один шанс
на миллион.

Решение на B — то же окно подтверждения (60 с, правила `blocked`/`off`/`busy`/`cooldown` те же),
с кодом и правами для A. «Связать» на B: A запоминается в режиме `contact` с выбранными правами
и добавляется в контакты B. На A: человек сверяет код и нажимает «Связать» — B запоминается
в режиме `contact` с правами, отмеченными на A, и добавляется в контакты A. Оба пишут `paired`
в журнал.

## Коды закрытия соединения

| Код | Значение |
|---|---|
| 0 | обычное: зритель ушёл / приложение закрывается |
| 1 | не впустили |
| 2 | хост отключил этот сеанс |
| 3 | аварийное отключение всех сеансов |
| 4 | сеанс продолжился в новом соединении того же зрителя |
| 5 | ошибка протокола |
| 6 | тишина дольше 20 с |

Если соединение закрыто без кода приложения (сеть пропала) или с кодом 6, зритель
переподключается с токеном до 55 с.

## Датаграммы

`[тип: 1][метка сеанса: 4 = первые 4 байта sid][данные]`

| Тип | Направление | Данные |
|---|---|---|
| 1 | зритель → хост, право control | seq u32, x u16, y u16 — движение мыши, 0..65535 от монитора |
| 2 | хост → зритель | seq u32, x u16, y u16 (0..65535 от монитора), флаги u8: 1 — курсор виден, 2 — он на этом мониторе |
| 3 | зритель → хост, право view | сегмент u32, получено кадров u32, показано кадров u32 |

## Быстродействие привязок iroh

Сгенерированные Python-привязки iroh 1.1–1.2 копируют каждый байт, отданный в Rust
(`write_all`, датаграммы), отдельно, в цикле Python. Это около 6 МБ/с и целое ядро
процессора — и для файлов, и для видео. `marinremote/net.py` при загрузке заменяет этот
метод на одно копирование `memmove`, но только если устройство буфера то же, что ожидает
код. Результат на одном ПК — 150–210 МБ/с.

## Однонаправленные стримы

`MRS1` + JSON-строка `{"t":"<вид>","sid":"<sid>",…}` + данные.

| Вид | Направление | Право | Данные |
|---|---|---|---|
| `video` | хост → зритель | view | заголовок `seg`, `mon`, `w`, `h`, `codec:"h264"`; кадры `[u32 длина][u64 время захвата, мкс][u8 флаги: 1 — ключевой][H.264 Annex-B]` |
| `input` | зритель → хост | control | JSON-строки: кнопки, колесо, клавиши (см. «Мышь и клавиатура») |
| `file` | обе стороны | files | заголовок `x`, `offset`; дальше сырые байты файла с `offset` до конца |
